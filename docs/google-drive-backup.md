# M4 — Google Drive Backup: Implementation Notes

> **Status:** Done and verified end-to-end (debug build **and** local release build).

## What changed from the original plan

The original proposal (see [proposal.md](proposal.md)) assumed `expo-auth-session` + the `drive.file` scope. Both turned out to be wrong once implementation started:

> **Library**: `expo-auth-session` was dropped in favor of `@react-native-google-signin/google-signin` (v16.1.2). It's a native module, which is **incompatible with Expo Go** — this forced a one-time switch from Expo Go to a custom **dev client** (`expo-dev-client` + `npx expo run:android`) for all local testing from here on.
>
> **Scope**: `drive.file` only grants access to files created via a picker/app-visible flow. Backups needed Drive's hidden **`appDataFolder`** (invisible in the normal Drive UI), which requires the `https://www.googleapis.com/auth/drive.appdata` scope instead.

## Google Cloud Console setup (as actually configured)

- One GCP project, OAuth consent screen in **Testing** mode, test user `george.replay@gmail.com`.
- Scopes: `https://www.googleapis.com/auth/drive.appdata`.
- Three OAuth clients under this project:
  - **TVApp Web client** (Web application type) — not used for sign-in directly; its Client ID is passed as `webClientId` to `GoogleSignin.configure()` because the library requires one even for Android-only apps.
  - **TvAppPersonal** (Android) — package `com.greplay.watchlog` (renamed from `com.gxenofontos.tvapp` after the repo went public — see [branding-and-release-build.md](branding-and-release-build.md)), SHA-1 of the **debug** keystore (`android/app/debug.keystore`, generated by `expo prebuild`).
  - A second **Android** client (release) — same package name, SHA-1 of the **local release keystore** (see the branding doc for how that keystore was created). Google ties one SHA-1 to one Android OAuth client, so debug and release builds each need their own registered client rather than sharing one.
  - Both clients' **package name** field was updated in place (not recreated) when the app was renamed — the SHA-1 pairing didn't need to change, only the package name string.

> The consent screen is still in **Testing** mode. Refresh tokens for test users can expire after ~7 days of inactivity, meaning `signInSilently()` (used by the launch auto-sync check) can occasionally fail and require an interactive re-sign-in via "Backup now". Moving to "Production" would need Google's verification review since `drive.appdata` is a sensitive scope — not worth it for a single-user personal app, so this is an accepted tradeoff, not a bug.

## Implementation

- `src/lib/google-auth.ts` — configures `GoogleSignin`, exposes `getDriveAccessToken()` (silent-then-interactive) and `getDriveAccessTokenSilent()` (silent-only, used by auto-sync, never prompts).
- `src/api/drive.ts` — thin wrapper around the Drive REST API v3: list files in `spaces=appDataFolder` by name, create-if-missing, then `PATCH .../upload/drive/v3/files/{id}?uploadType=media` to write JSON content. Chose this two-step create-then-patch approach over multipart/FormData/Blob uploads, which are unreliable in React Native.
- `src/db/queries.ts` — added `exportAllData()` / `importAllData()` (payload = all four tables as JSON) and `getLastSyncedAt()` / `setLastSyncedAt()` backed by the pre-existing `sync_meta` key/value table.
- `src/lib/backup.ts` — `backupNow()`, `restoreFromDrive()` (wrapped in a `db.transaction()` delete-then-reinsert for atomicity), and `maybeAutoSync()` (best-effort, silent, only runs if 7+ days stale and a Drive session already exists — never shows a sign-in prompt on its own).
- Settings screen (originally `profile.tsx`, now `src/app/(tabs)/settings.tsx` post-redesign) — "Backup now" / "Restore from Drive" buttons (with a destructive-style confirmation dialog before restore) and a "Last backed up …" timestamp.
- `src/app/_layout.tsx` — calls `maybeAutoSync()` once on launch, alongside hiding the splash screen.

## Verified

- Full OAuth flow on a real device/emulator: account picker → "Google hasn't verified this app" interstitial (expected in Testing mode) → `drive.appdata` consent screen → back to app.
- "Backup now" uploads and updates the last-synced timestamp.
- "Restore from Drive" round-trips correctly: followed a show, then restored an older (pre-follow) backup without re-backing-up first, and confirmed the follow was reverted — proving the transactional import actually overwrites local state rather than merging.
- Re-verified the whole flow again on the **local release build** after registering its SHA-1 (see [branding-and-release-build.md](branding-and-release-build.md)) — backup succeeded there too.
